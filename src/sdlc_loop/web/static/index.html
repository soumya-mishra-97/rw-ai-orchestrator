          Robert Walters AI-Orchestrator

          AI-powered multi-agent SDLC planning platform with evaluator gates.

          Enter one feature requirement. A Master Orchestrator validates it and runs it through five specialist agents, from product goals to a tested implementation slice. An independent Evaluator scores every handoff, retries weak work with specific feedback, and escalates to a human when quality does not recover. Every model call, score and decision is written to a tamper-evident audit trail.

          How it works

          1. RequirementYou describe what to build. Personal data is redacted before anything else sees it.
          2. Master OrchestratorValidates the requirement, plans which agent runs on which model, and dispatches the run.
          3. Product ManagerGoals, success metrics, constraints and scope.
          4. Business AnalystUser stories with testable acceptance criteria, traced to the goals.
          5. Solutions ArchitectComponents, integration approach, risks with mitigations, decision records.
          6. DeveloperRunnable code for the highest-value stories; honest stubs for the rest.
          7. QA EngineerTest cases mapped to acceptance criteria, plus the measured result of checking the code.
          8. Final ReportAll artifacts, every decision and cost, downloadable as a formatted SDLC Execution Report (PDF).

          After the Product Manager, Business Analyst, Architect and Developer, the Evaluator scores the handoff before the next agent starts. A failed handoff goes back to the same agent with feedback.

          Agent responsibilities

          Master Orchestrator

          The Master Orchestrator is not a language model. It is deterministic code that owns the workflow, so the order of agents and every quality gate behave the same way on every run.
          • Manages the workflow: validates the requirement, plans the run and dispatches it.
          • Routes tasks: each agent runs on the model its risk level calls for; the Architect and Developer always use the stronger model.
          • Maintains shared state: every artifact lives in the workflow state, checkpointed after each step so a paused run survives a restart.
          • Handles retries: the Evaluator's verdict decides the next step (pass, retry with feedback, or escalate to a human).
          • Records audit events: validation, planning, every call and every decision go to an append-only, hash-chained log.

          Live mode

          Agents call Claude: Haiku for extraction-style work and first-pass judging, Sonnet for design, code and borderline re-scoring. Any requirement produces real generated output, and tokens and cost are reported by the API.

          Demo mode

          No API key needed. Curated examples replay hand-authored outputs; any other requirement runs through the local simulator (template content and a rule-based judge). No model is called, the cost is $0, and every such run is labelled.

          Switching with ANTHROPIC_API_KEY

          At startup the server looks for ANTHROPIC_API_KEY (environment or .env) and checks it with one free API call. A working key starts live mode; no key, or a rejected key, starts demo mode and the status bar explains why. Force a mode with SDLC_MODE=live or SDLC_MODE=demo. Both modes run the same orchestrator, evaluator, retry logic and audit trail; only the model behind the LLM service changes.

          Evaluation & retry

          Every handoff is scored from 1 to 5 on five dimensions:

            Score is the mean of the five. Pass rule: . The verdict is computed in code from the scores, so a model can never approve its own work.

            Attempt 1Agent's default model
            Attempt 2Same model, evaluator feedback added
            Attempt 3Stronger model, full feedback history
            Human reviewAccept as is, retry with guidance, or abort

            A score that lands between 3.0 and 3.99, or that would page a human, is re-scored by the stronger judge first. A structural defect (for example code that does not parse) is rejected by a zero-cost pre-gate before any judge runs.

            Example: the Evaluator rejects the PM's first draft

            PM Attempt 1 produces a thin brief (two goals, unmeasurable metrics).
            Evaluator Score 3.8 (below 4.0) → RETRY with feedback: "Expected 3-5 measurable business goals, found 2."
            PM Attempt 2 revises the brief using the feedback.
            Evaluator Score 4.6 → PASS, and the Business Analyst starts.

            Token & cost optimisation

            Model routing

            Cheap Haiku for PM, BA, QA and first-pass judging; Sonnet only where mistakes are expensive (Architect, Developer, final retries).

            Tiered evaluator

            The stronger judge re-scores only borderline results or results about to page a human.

            Prompt caching & reuse

            A byte-identical shared prefix (rules and rubric) is cached per model and reused by every agent.

            Minimal context

            Each agent receives only the upstream artifact it needs, never the whole history.

            Zero-cost pre-gate

            Structural defects are rejected in code before any judge tokens are spent.

            Simulator fallback

            Without a key, demo mode exercises the full workflow for $0.

            Token tracking

            Every call's input, output and cache tokens and cost are logged; Run Metrics shows them per agent.

            Batch API

            Evaluation runs can go through the Message Batches API at half price.

            Governance & security

            • PII handling: the requirement is redacted (emails, card numbers, phone numbers and more) before any model call or log write, and audit payloads are redacted again.
            • Audit trail: append-only and hash-chained; sdlc verify-audit detects tampering.
            • Secrets: the API key is read only by the Anthropic SDK; it is never stored in settings, logs or run state. .env is git-ignored.
            • Access control: with SDLC_API_KEYS set, keys map to roles; only a reviewer can resume an escalated run, and their identity is recorded.
            • Environment variables: every setting is configured through SDLC_* variables or .env; see .env.example.
            • Browser: a strict Content-Security-Policy, and model output is always shown as text, never executed as HTML.

            Troubleshooting

            “Port 8000 is already in use”
            Another copy is running. Stop it with lsof -ti tcp:8000 | xargs kill, or start on another port with sdlc serve --port 8001.
            The status bar says Demo Mode although I set a key
            The status bar shows the reason. Put ANTHROPIC_API_KEY in the environment or in .env in the directory you start from, then restart.
            A run stops at “Needs review”
            Expected: the Evaluator escalated. Use the review panel to accept, retry with guidance, or abort.
            A live run shows Failed
            The Final Result and Execution Timeline show the API error. Transient errors are retried automatically first.
            Nothing happens when I click Generate Intelligent SDLC Blueprint
            If API keys are enabled, enter one in the sidebar. Otherwise check the server log.
