# Token and cost optimisation

Seven levers are implemented. Each one:

- can be switched off with an environment variable, so its effect can be measured as an ablation;
- is logged per call as a counterfactual in the audit trail, so its effect shows up on every normal run;
- has a stated tradeoff.

## The levers

### 1. Model routing by risk, not by default

**What.** Haiku 4.5 ($1/$5 per MTok) runs PM, BA and QA. Sonnet 5 ($2/$10) always runs Architect and Dev, plus any final retry or post-critical retry. See [`llm/model_router.py`](../src/sdlc_loop/llm/model_router.py).

**Measured by.** Each call logs `cost_all_tier2_usd`, the same token counts re-priced on Sonnet. The `--routing-policy all_tier2` ablation measures the baseline for real, because Sonnet may write longer or shorter output than Haiku.

**Tradeoff.** Haiku may need more retries on PM and BA. The metric that decides is **cost per completed run including retries**, not cost per call. If Haiku's first-attempt pass rate on BA→Architect turns out low enough that retries erase the saving, the fix is one line: move BA's default tier. Architect and Dev are deliberately *not* routed down. A bad design costs a Sonnet Dev call, a QA call, several judge calls and possibly a human, which is far more than the Haiku saving.

### 2. Tiered evaluator

**What.** The Haiku judge runs first. The Sonnet judge re-scores only borderline results (3.0 ≤ mean < 4.0) and results about to page a human.

**Measured by.** The share of evaluations resolved by Tier 1 alone, and the number of Tier 2 confirmations. The `--no-tiered-evaluator` ablation puts every judgement on Sonnet.

**Tradeoff.** A Haiku *false pass* is never re-checked, because clear passes skip confirmation. That is the risk this lever buys, and it is why the judge benchmark reports its false-rejection and detection rates, and why the human-agreement study tracks false passes specifically.

### 3. Deterministic pre-gate

**What.** Structural defects are rejected in code before any judge call: untraced stories, out-of-range goal indices, risks without mitigations, code that does not parse, stories silently skipped. See [`quality/checks.py`](../src/sdlc_loop/quality/checks.py).

**Measured by.** The count of `deterministic` verdicts, each of which is at least one judge call avoided (two when a confirmation would have run).

**Tradeoff.** The rules have to be unambiguous, or they cause wasted retries. Judgement calls such as "is this metric vague?" are therefore advisory only: they are passed to the judge as hints and never block.

### 4. Prompt caching, and why it matters *less* than you might expect here

**What.** The system prompt is laid out as `[shared preamble + rubric]` (breakpoint 1, byte-identical for every persona) followed by `[persona prompt]` (breakpoint 2). Only the user message varies. Because caches are model-scoped, one entry per model serves every persona. See [`llm/cache.py`](../src/sdlc_loop/llm/cache.py).

**The measured constraint.** The static prefix is about 1,750–1,890 tokens (preamble plus rubric about 1,570, persona prompt 180–320).

| Model | Minimum cacheable prefix | Does our prefix cache? |
|---|---|---|
| Sonnet 5 (Architect, Dev, Tier 2 judge) | 1,024 | **Yes.** Reads bill at 0.1× |
| Haiku 4.5 (PM, BA, QA, Tier 1 judge) | 4,096 | **No.** Silently uncached |

This is asserted in `test_cache_layout_and_eligibility` and reported as the measured cache-hit rate. It is not assumed.

**Should the Haiku prefix be padded past 4,096?** The arithmetic, per Haiku call:

- Today: about 1,885 uncached tokens, roughly $0.0019.
- Padded to 4,096 and cached: a read costs 0.1 × 4,096 = 410 token-equivalents, roughly $0.0004. The cache write costs 1.25 × 4,096, and it happens about once per 5-minute window.
- A run makes about 8 Haiku calls, so padding would save roughly $0.007 per run, **provided the extra ~2,200 tokens are useful**, for example one worked exemplar per artifact type.

I did not do it. The saving is under 10% of a run's cost, and padding with filler is a quality risk with no upside. It belongs in a quality experiment ("do exemplars raise first-attempt pass rates?") where the caching saving comes along for free.

**The honest conclusion.** At these prompt sizes, caching is a minor lever. The money is in output tokens (Dev's code, Sonnet's adaptive thinking) and in avoided calls (retries, judge confirmations). That is why levers 1–3 and 7 come first.

### 5. Minimal context passing

**What.** Each persona receives only its immediate upstream artifact(s); see [architecture §4](architecture.md#4-minimal-context-passing). The full-history alternative grows with every stage, because QA would receive the request, the brief, the requirements, the design, the implementation and every evaluation.

**Measured by.** Every call logs `minimal_context_tokens` and `naive_context_tokens` (estimated). The `--context-policy full_history` ablation measures the real difference, including any quality effect.

**Tradeoff.** A persona cannot notice an upstream problem it never sees. The mitigation is that the brief's constraints are carried explicitly into the Architect, Dev and judge contexts, since that is the one piece of history every later stage needs.

### 6. Structured outputs, plus one bounded repair

**What.** `output_config.format` carries a JSON schema generated from the Pydantic models, so the API constrains decoding to valid JSON. Pydantic then checks the constraints the API cannot express, such as unique ids and score ranges. On failure there is **one** repair call with the validation error appended.

**Measured by.** The parse-failure rate (`parse_failure` audit rows ÷ calls). Every failure is a wasted call, and every repair is logged.

**Tradeoff.** The first use of a new schema adds compilation latency, after which the schema is cached for 24 hours. Schemas also cannot use free-form dicts, which is why the artifacts use typed sub-models.

### 7. Batch API for evaluation runs

**What.** A pipeline is sequential within a run but independent across runs. [`llm/batch_client.py`](../src/sdlc_loop/llm/batch_client.py) parks each run's pending call. Once every concurrent run is waiting, or after 20 s, it submits all parked calls as a single Message Batch. The graph code is unchanged. With 9 concurrent runs, each pipeline stage becomes about one batch.

**Measured by.** `cost_sync_usd` versus the billed cost on batched calls. The expected saving is exactly 50% of token cost.

**Tradeoff.** Each stage can take minutes to hours, so this is used only for evals, never for interactive runs. Per-call latency becomes meaningless: batched calls are excluded from latency percentiles. Cache hits within a batch are best-effort.

### Also in the design

- **Effort control.** Sonnet runs with `effort=medium` (`SDLC_TIER2_EFFORT`), which bounds adaptive-thinking tokens. Those are billed as output tokens at the highest rate in the system.
- **Revise, don't regenerate.** Retries include the previous attempt, so the model makes targeted fixes instead of producing a fresh artifact that may introduce new defects. This costs more input tokens per retry and is expected to need fewer retries. It can be switched off with `SDLC_INCLUDE_PREVIOUS_ATTEMPT_ON_RETRY=false` to measure the effect.
- **Bounded worst case.** At most 3 attempts per handoff, at most 2 judge calls per attempt and 1 repair per call, which caps the cost of a pathological run. The expensive failure mode, an infinite retry loop, is structurally impossible.

## What this looks like at enterprise scale

The spend that matters is **cost per completed, human-free run**, not cost per call:

- A run that escalates costs its tokens *plus* a reviewer's time, which is far more than the tokens.
- A lever that cuts tokens by 20% but raises the escalation rate by 5 percentage points is a net loss.

That is why the eval reports cost and escalation rate side by side, and why the ablations re-run the full pipeline instead of re-pricing single calls.
